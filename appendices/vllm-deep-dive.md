## 附录 E：vLLM 定位与推理引擎选型

> [← 返回主文档](../AGENT_PLATFORM_BLUEPRINT.md)

> **背景**：澄清「vLLM 是什么」「Qwen 开源模型如何部署」「为什么蓝图坚持 vLLM 用 Python」三个核心问题。本附录是模型部署维度的决策依据。

### E.1 核心澄清：vLLM 不是模型，是推理引擎

```
常见误解：
  ❌ 错误理解：vLLM = 本地模型
  ✅ 正确理解：vLLM = 跑模型的「发动机」，模型是「汽油」

类比：
  vLLM        = Web 服务器（如 Nginx）
  Qwen 模型    = 网站代码（静态文件）
  HTTP API    = HTTP 协议
```

三者关系：

```
┌──────────────────────────────────────────────────────┐
│                      vLLM（发动机）                    │
│  Python 编写的高性能推理服务器                            │
│  特性：                                                 │
│  - PagedAttention（显存管理，类似虚拟内存）               │
│  - Continuous Batching（连续批处理，吞吐量 10-20x）      │
│  - CUDA 内核优化（直接调 GPU）                           │
│  - 对外暴露 OpenAI 兼容 HTTP API                         │
└──────────────────────┬───────────────────────────────┘
                       │ 加载
                       ▼
┌──────────────────────────────────────────────────────┐
│              Qwen2.5-72B（汽油/模型权重）                │
│  本质：一堆 .safetensors 文件（约 144GB）                │
│  语言无关：权重就是数字矩阵，和 Python/C# 无关             │
│  这些文件谁都能读，但「怎么高效推理」才是难点              │
└──────────────────────────────────────────────────────┘
```

> **本质**：模型权重是语言无关的数字矩阵；推理引擎负责加载权重并高效计算。vLLM 是众多推理引擎中性能最强的一个，恰好用 Python 编写。

### E.2 Qwen（千问）的两种产品形态

```
┌─────────────────────────────────────────────────────────────┐
│  方式一：用阿里云的 Qwen API（商业服务）                        │
│  ─────────────────────────────────────────                  │
│  - 不用自己部署，阿里帮你跑                                    │
│  - 直接 HTTP 调用：https://dashscope.aliyuncs.com            │
│  - 完全不需要 Python，不需要 GPU                              │
│  - 按调用次数/token 付费                                      │
│  - C# 直接 HTTP 调用即可                                      │
│                                                              │
│  ✅ 这种情况：根本不用 vLLM，也不用 Python！                  │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│  方式二：自己部署开源 Qwen（本地/私有云）                      │
│  ─────────────────────────────────────────                  │
│  - 从 HuggingFace 下载 Qwen2.5-72B 权重文件                  │
│  - 需要自己买 GPU 服务器来跑                                   │
│  - 需要一个「推理引擎」来加载权重并提供 API                    │
│  - 推理引擎的选择决定用什么语言                                │
│                                                              │
│  ❓ 这种情况：要不要 Python，取决于选哪个推理引擎              │
└─────────────────────────────────────────────────────────────┘
```

### E.3 推理引擎选型对照表

| 推理引擎 | 主语言 | 性能 | 易用性 | 适合 Qwen 本地部署 | 说明 |
| :--- | :--- | :--- | :--- | :---: | :--- |
| **vLLM** | Python | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ✅ | **官方推荐，性能最佳**，蓝图默认选择 |
| TGI (HuggingFace) | Python/Rust | ⭐⭐⭐⭐ | ⭐⭐⭐ | ✅ | 可用，生态完善 |
| Ollama | Go | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ✅ | 最省心，适合开发/测试，性能只有 vLLM 的 30-50% |
| llama.cpp | C++ | ⭐⭐⭐ | ⭐⭐ | ✅ | 量化版可用，性能一般 |
| TensorRT-LLM | C++/Py | ⭐⭐⭐⭐⭐ | ⭐⭐ | ✅ | NVIDIA 极致性能，调优复杂 |
| ONNX Runtime | C++(原生) | ⭐⭐ | ⭐⭐ | ⚠️ | 慢，功能受限 |
| ML.NET | C# | ⭐ | ⭐ | ❌ | 几乎不能用 |

### E.4 三种主流选择对比

#### 选项 A：vLLM（Python）—— 蓝图推荐，性能最强

```bash
# 一行命令部署 Qwen
docker run --gpus all -p 8001:8000 \
  vllm/vllm-openai:latest \
  --model Qwen/Qwen2.5-72B-Instruct
```

**为什么选它**：PagedAttention + Continuous Batching 让单卡吞吐量提升 10–20 倍，生产环境唯一选择。

#### 选项 B：Ollama（Go）—— 不想碰 Python 的最佳替代

```bash
# Ollama 是 Go 写的，对用户隐藏了 Python
ollama run qwen2.5:72b
# 自动暴露 http://localhost:11434/v1（OpenAI 兼容）
```

**特点**：底层用 llama.cpp（C++），Go 做服务封装。Ollama 二进制本身不含 Python，但性能只有 vLLM 的 30-50%。**适合开发/测试，不适合高并发生产。**

#### 选项 C：直接用云 API —— 最省事，零部署

```csharp
// C# 直接调用阿里云 DashScope API，什么都不用部署
var client = new OpenAIClient(
    apiKey: config["DashScope:Key"],
    endpoint: new Uri("https://dashscope.aliyuncs.com/compatible-mode/v1"));

// 调用千问商业 API
var response = await client.ChatCompletion.CreateAsync(
    model: "qwen-max",
    messages: ...);
```

**特点**：连服务器都不用买，按量付费。如果数据敏感度不高，这是最优解。

### E.5 为什么蓝图坚持「vLLM 用 Python」

#### 原因一：性能差距巨大，无法忽视

```
同样一块 A100 GPU，跑 Qwen-72B：

vLLM（Python + CUDA）：     ~3000 tokens/秒
Ollama（Go + llama.cpp）：   ~1000 tokens/秒
ONNX Runtime（C# 进程内）：    ~300 tokens/秒

差距来源：
vLLM 的 PagedAttention 是用 CUDA C++ 写的内核，
只是用 Python 做了胶水层。你以为在跑 Python，
其实 90% 时间在跑 CUDA。
```

#### 原因二：进程隔离 > 语言洁癖

```
蓝图第 207 行的核心原则：「永远不在 C# 进程内跑大模型」

✅ 推荐架构（进程隔离）：
┌──────────────┐   HTTP   ┌──────────────────┐
│ C# 平台进程   │ ───────→ │ vLLM 进程（Python）│
│ 主业务逻辑    │ ←─────── │ 专门做推理        │
└──────────────┘  响应    └──────────────────┘
好处：
- C# 进程崩了不影响推理服务
- 推理服务可以单独扩容（加 GPU 节点）
- 可以混用不同语言的最佳工具

❌ 反例（进程内推理，性能差）：
┌──────────────────────────────┐
│ C# 进程                       │
│ 业务逻辑 + ONNX Runtime 推理   │  ← 卡顿、占内存、影响主流程
└──────────────────────────────┘
```

#### 原因三：vLLM 的 Python 只是「外壳」

```
vLLM 的内部调用链：

你的请求
  → Python API 层（< 1% 时间）
    → PyTorch（C++ 后端，~5% 时间）
      → 自定义 CUDA 内核（PagedAttention，~90% 时间）
        → GPU 计算

所以 vLLM 名义上是 Python，
实际 95% 的计算在 C++/CUDA 里。
Python 只是「调度员」，不是「干活的人」。
```

### E.6 vLLM 在路由层中的定位

> **关键认知**：vLLM 和云模型在路由层中是**完全平等**的候选。谁当主、谁当备，纯由 Yaml 策略决定，不是代码问题。

#### vLLM 不是必须当「最后兜底」，它有三种典型定位

```
场景一：成本敏感（vLLM 当主模型，省钱）
  请求 → local-llm (vLLM) ──✅ 主力（GPU 已买，推理免费）
         gpt-4o (云)        ── 备用（本地挂了才用）

场景二：质量敏感（vLLM 当兜底，保可用性）
  请求 → gpt-4o ──✅ 主力（质量最好）
         local-llm (vLLM) ── 兜底（云模型挂了/超预算才用）

场景三：数据敏感（vLLM 当唯一选择，保隐私）
  请求 → local-llm (vLLM) ──✅ 唯一选择，不配置任何云模型
```

#### 三种策略的 Yaml 配置对比

```yaml
# 场景一：vLLM 当主模型（省钱策略）
routing:
  candidates:
    - modelId: "local-llm"       # ← 主模型（免费）
      weight: 100
    - modelId: "deepseek"        # ← 备用（便宜）
      weight: 80
    - modelId: "gpt-4o"          # ← 最后兜底（贵，但保底）
      weight: 60

# 场景二：vLLM 当兜底（保可用性策略）
routing:
  candidates:
    - modelId: "gpt-4o"          # ← 主模型（质量最好）
      weight: 100
    - modelId: "deepseek"        # ← 第一备用
      weight: 80
    - modelId: "local-llm"       # ← 最后兜底（永不宕机，但永不掉线）
      weight: 60

# 场景三：vLLM 当唯一选择（数据隐私策略）
routing:
  candidates:
    - modelId: "local-llm"       # ← 唯一候选，不配任何云
      weight: 100
  allowFallbackToCloud: false    # ← 禁止 fallback 到云
```

#### 为什么 vLLM 常被当成「最后兜底」

```
1. 永不掉线
   云模型会限流、会宕机、会维护
   你自己的 vLLM 只要 GPU 没坏，永远可用
   → 所以适合做"最后的防线"

2. 成本固定
   云模型按 token 收费，用量暴增时账单吓人
   vLLM 是你买的 GPU，推理"免费"（边际成本≈0）
   → 当云模型超预算时，自动切到 vLLM

3. 可控性
   云模型可能变更、下线、调价
   你自己的 vLLM 完全可控，模型版本永远不变
   → 适合做"压舱石"
```

### E.8 选型决策树

```
你想用 Qwen？
│
├─ 数据可以走云端？ ─── YES ──→ 直接调阿里云 DashScope API
│                                ✅ 不用 Python，不用 GPU，C# HTTP 调用即可
│
└─ 必须私有部署？
    │
    ├─ 需要高并发/生产环境？
    │   └── YES ──→ vLLM（Python）
    │              ✅ 性能最强，蓝图推荐
    │              接受 Python 只是个「部署组件」，用 Docker 隔离
    │
    ├─ 只是开发测试/个人用？
    │   └── YES ──→ Ollama（Go，无可见 Python）
    │              ✅ 装一行命令，性能够用
    │
    └─ 死活不想碰 Python，且愿意牺牲性能？
        └── → llama.cpp（纯 C++）+ 自己写 HTTP 封装
            ⚠️ 性能一般，要自己维护
```

### E.9 项目语言占比澄清

```
"vLLM 用 Python" ≠ "你的项目是 Python 项目"

你的项目语言分布：
┌──────────────────────────────────────┐
│  C# 代码（你的核心）：~95%              │
│  - 全部业务逻辑                        │
│  - 全部 DDD 分层                       │
│  - 前端 React                         │
│                                      │
│  Python 代码（推理组件）：~5%           │
│  - 只是 Docker 里的 vLLM 镜像          │
│  - 你不写 Python 代码，只是 docker run │
│  - 对 C# 来说它就是一个 HTTP API        │
└──────────────────────────────────────┘

类比：你用 Redis 不会在乎它是 C 写的，用 PostgreSQL 不会在乎它是 C 写的
     ——vLLM 也一样，它是「基础设施」，用 Docker 跑起来，
     C# 通过 HTTP 调用，仅此而已。
```

> **一句话总结**：vLLM 就是用 Python+CUDA 搭的「私人 OpenAI 微服务」，对 C# 平台而言它和其他云模型完全平等——同样是 HTTP 调用、同样的 OpenAI 兼容格式。它是不是「最后兜底」取决于 Yaml 路由策略：省钱场景下它是主模型，质量场景下它是兜底，隐私场景下它是唯一选择。模型权重（如 Qwen）是语言无关的，推理引擎选 vLLM 是因为性能最强，而非因为必须用 Python。
