# Codebase Optimizer Skill

## 触发条件

满足以下任一条件即触发：

1. **用户显式请求**：代码优化、审查、重构、代码体检、代码分析、项目健康检查，或任何涉及代码质量评估/改进的请求。
2. **项目质量治理要求（阶段结束时）**：当所在项目的质量治理文档要求在阶段完成时运行本技能时也触发。典型条款（见本仓库 `docs/quality/QUALITY-GATE.md`）：**每阶段完成后、该阶段最后一笔（或倒数第二笔）提交前**，须跑 `codebase-optimizer` 做全库多维度健康检查（含桩代码替换进度、生产就绪度）；Phase 6+ 强制，Phase 5 为过渡期（允许 `not_run`）。执行阶段收尾提交前，应先核对项目治理文档确认是否需本技能，不要仅按"是否有用户请求"判断。

## 全局约定

- **状态目录**: 项目根目录 `.codebase-optimizer/`
- **文件命名**: `status.md` | `rounds/round-NN-report.md` | `rounds/round-NN-tasks.md` | `changelog.md` | `final-summary.md`
- **严重度**: P0=崩溃/数据丢失/安全漏洞；P1=违反最佳实践有潜在风险；P2=值得改进但不紧急
- **红线**: 不修改第三方库和生成代码（node_modules, vendor, dist, build, .gitignore所列目录）
- **扫描范围**: 分析时跳过 .gitignore 所列目录及非源码目录（node_modules, vendor, dist, build, .git, __pycache__, .next, .venv 等）。**多栈项目**：后端源码（如 `src/*/*.cs`）与前端源码（如 `src/AgentPlatform.Web/src` 下的 `.ts`/`.tsx`）**都纳入扫描**；前端仅跳过 `node_modules`/`dist`/`build`。
- **轮次上限**: Step 0 根据项目规模自动确定（默认 5 轮）。超出上限自动收尾并告知用户。未修问题写入 final-summary 的"已知遗留问题"章节
- **容错**: 读取历史轮次文件时若文件不存在，将当前轮次重置到已有记录的最大轮次 + 1
- **超时策略**: 交互模式下询问用户时若长时间无响应，保存 `current_step` 退出，下次恢复

## 运行模式

Step 0 初始化后询问用户选择运行模式，整个流程中模式不再变更：

| 模式 | 确认需求 | 适用场景 |
|------|---------|---------|
| **交互模式** | 每项决策告知用户，等待确认后继续 | 首次运行、对项目不熟悉、希望逐步 review |
| **自动化模式** | 零确认，所有决策由 Agent 自主执行 | 二次运行、对 Skill 熟悉、希望一键完成 |

**模式差异对照**：

| 环节 | 自动化模式 | 交互模式 |
|------|-----------|---------|
| Step 1 报告交付 | 自动进入 Step 2 | 询问用户是否进入修复 |
| Step 3 风险操作 | 直接执行+记录 | 批量列出，等待用户确认 |
| Step 4 决策 | 直接执行 | 等待用户确认 |
| Step 5 阶段切换 | 自动切换 | 询问用户是否继续 |
| 超时无响应 | 不适用（无等待） | 存档 current_step 后退出 |

**自动化模式额外行为**：
- 创建统一 Git 分支 `codebase-optimizer/{日期}`，整个优化过程的所有 commit 都在该分支上
- 每轮优化完成后单独 commit + push，方便人工逐轮 review
- 所有修改记录到 `changelog.md`
- 不等待用户确认，直接执行

## 边界规则（覆盖其他所有行为）

- **用户说"停"**: 先更新 `status.md` 的 `current_step` 存档当前进度，再停止
- **每轮告知进度**: 每次更新 `status.md` 后，在对话中向用户报告当前进度（如："阶段1 Round 3/5，累计发现问题 12，已修复 8（67%）"）
- **每轮结束**: 交互模式等待用户回复；自动化模式直接继续，在对话中告知进展

## 多栈项目支持（前端 + 后端）

当项目同时含后端（.NET/Java/Go 等）与前端（React/Vue/TypeScript 等）时，按以下规则一并优化：

- **扫描范围**：后端源码目录 + 前端源码目录（`.ts`/`.tsx`）都纳入七维度扫描；`node_modules`/`dist`/`build` 仍跳过。
- **语言检测**：Step 0 分别统计前后端文件数与行数，识别主语言（如 C# + TypeScript）。
- **验证命令分流**：
  - 后端：沿用 `dotnet build` / `dotnet test`（及 `dotnet list package --vulnerable`）。
  - 前端：优先调用项目统一 QA 脚本入口（等价于后端 build+test 的回归闸门）。本仓库前端为 `src/AgentPlatform.Web/scripts/qa.mjs`，调用 `node scripts/qa.mjs`（可选 `--e2e` 追加端到端）；结构化报告写入 `qa-report.json`。若无统一 QA 脚本，则分别调用 `npx tsc --noEmit` / `npx eslint .` / `npx vitest run` / `npx playwright test`。
  - 每轮修复后，后端跑 `dotnet build`+`dotnet test`、前端跑 QA 脚本，**两者都绿**才算回归通过。
- **桩代码替换进度维度**：该维度针对后端蓝图 Stub 清单；前端无对应清单时标记为 N/A，不强行套用。
- **前端专项检查项**：补充进对应维度（XSS/`dangerouslySetInnerHTML`、未捕获 Promise、hook 依赖、`React key`、`any` 泛滥、硬编码密钥、eslint/tsconfig strict、未用依赖等），详见 `checklists.md` 各维度"前端"子项。

## 工作流

### Step 0: 初始化

`status.md` 不存在时执行：

1. 创建 `.codebase-optimizer/rounds/` 和 `.codebase-optimizer/backups/` 目录
2. 快速摸底项目规模：统计文件总数和代码行数，按以下标准确定项目类型：
   - 小型（< 20 文件）：任务数上限 4 个/轮，阶段上限 3 轮
   - 中型（20-200 文件）：任务数上限 8 个/轮，阶段上限 5 轮
   - 大型（> 200 文件）：任务数上限 12 个/轮，阶段上限 8 轮
3. 扫描项目全景摸清语言/框架/结构，结果写入 `status.md` 的"项目信息"中
4. 此时加载 templates.md，使用其中的 status.md 模板写入完整的 `status.md`，含项目类型、自适应参数和运行模式占位
5. 通知用户初始化完成 → 询问用户选择**交互模式**还是**自动化模式**
6. 将模式写入 `status.md`，开始 Round 1

### Step 1: 分析与报告生成

1. 读取 `status.md`，恢复当前阶段、轮次、`current_step`、运行模式以及已保存的项目扫描结果
2. 直接利用 Step 0 已保存的项目扫描结果作为基础，深入分析模块间依赖关系（追踪 import/require/include 语句，识别循环依赖和耦合）
3. 根据当前阶段，此时加载 **checklists.md**，按逐维依次扫描：阶段1按架构→代码质量→正确性→测试的顺序，阶段2按性能→安全→工程化的顺序。每完成一个维度记录发现，再进行下一维度
4. 去重：若当前轮次 ≥ Round 2，读取上一轮 `rounds/round-NN-tasks.md`，检查每个问题的任务状态是否为 `[x]`（已完成），已修复的跳过；再对比已有报告已记录的问题，去重后只保留新发现的。Round 1 无上一轮，跳过此步
5. 此时加载 templates.md 的报告模板部分，生成 `rounds/round-NN-report.md`
6. 向用户交付报告。**交互模式例外**: 询问"是否进入修复模式？"若选否，流程结束
7. 更新 `status.md` 中的进度统计和 `current_step`

### Step 2: 生成任务清单

根据报告生成 `rounds/round-NN-tasks.md`（此时加载 templates.md 的任务模板部分）：

- 中粒度：一个任务对应一个文件或一个主题
- 每轮最多 N 个任务（N 在 Step 0 根据项目规模确定，默认 8）
- 排序：P0 → P1 → P2
- 每个任务含文件路径、行号、具体修复步骤
- 同文件同维度问题合并为单个任务；不同维度即使在同一文件也分列独立任务
- 若发现的问题超过每轮上限，优先取 P0+P1 生成任务，按严重度排序取前 N 个；若本轮无 P0/P1 问题，直接从 P2 中取优先级最高的 N 个；未被排入本轮的 P2 问题推迟到本阶段内下一轮优先处理，连续被推迟两轮则强制排入
- 更新 `status.md` 中的 `current_step` 为 `task_generated`
- 若任务清单为空（0 个任务），跳过 Step 3，直接进入 Step 4 决策

### Step 3: 执行任务

1. **安全检查与备份**：
   - 检查项目根目录是否包含 `.git` 目录
   - **自动化模式**: 
     - 若是 Git 仓库：Round 1 首次执行时创建统一分支 `codebase-optimizer/{日期}`（如 `codebase-optimizer/2026-06-11`），后续轮次在此分支上增量 commit；如果分支已存在则 checkout 到该分支
     - 若不是 Git 仓库：自动备份将被修改的文件到 `.codebase-optimizer/backups/`，文件名加 `.bak` 后缀
   - **交互模式**: 若是 Git 仓库，建议用户创建优化分支；若不是，自动备份文件

2. **执行方式**：直接按 P0 → P1 → P2 逐个执行。每个任务：更新 `current_step` → 读取文件 → 执行修改 → 更新任务状态 `[x]` → 记录变更到 `changelog.md`。**交互模式例外**: 将本轮涉及删除/重命名/接口变更的任务一次性列出，询问用户是否统一允许执行，用户可逐一接受或拒绝。拒绝的标记为 `[-] 已拒绝`

3. **changelog 记录**（自动化模式）：每个修改完成后，追加记录到 `.codebase-optimizer/changelog.md`，格式为：
   ```
   ## Round {NN}
   ### {当前日期}
   - [R{NN}-T1] {重构/重命名/修复/格式化/删除} | {文件路径}:{行号} | {修改摘要}
   ```

4. **回归验证**：全部执行完成后，对修改过的文件做快速回归检查，确认是否引入新的明显问题。**多栈项目**：后端改动跑 `dotnet build`+`dotnet test`，前端改动跑 `node scripts/qa.mjs`（`src/AgentPlatform.Web`），两者都绿才算通过；检查结果写入本轮报告备注和 changelog
5. **本轮 commit + push（自动化模式 + Git 仓库）**：git add 所有本轮修改过的源码文件 → git add `.codebase-optimizer/` 目录（含报告/任务清单/changelog 等优化记录，方便 reviewer 查看上下文；若不想入库可后续在 `.gitignore` 中添加 `.codebase-optimizer/`）→ git commit -m `"codebase-optimizer: Round {NN} 优化 — {阶段名}"` → git push origin `codebase-optimizer/{日期}`（若 push 失败，告知用户并将变更保留在本地分支中，提示用户手动推送）→ 更新 `current_step` 为 `all_tasks_done`

### Step 4: 轮次评估与决策

读取 `status.md`，确认 `current_step` 为 `all_tasks_done` 后再进入决策，否则从中断点恢复。

按以下优先级从上到下依次评估，命中即止：

1. 任务清单中有未完成任务 → 继续执行，不进入决策
2. 本轮发现问题为 0 → 当前阶段收尾
3. 本轮问题数 ≥ 5 → 建议进入下一轮
4. 本轮修复引发了新问题（Step 3 快速验证检出）→ 建议进入下一轮
5. Round 1 且问题数 < 5 → 建议再跑一轮确认无遗漏
6. 本轮 < 3 且上一轮也 < 3 → 当前阶段收尾 / 阶段完成
7. 连续 3 轮问题数在 3-4 之间 → 询问用户是否继续，若用户不回应则自动收尾
8. 以上均不命中 → 询问用户是否继续

告知用户决策结果 → 更新 `status.md`。**交互模式例外**: 等待用户确认后再更新

### Step 5: 阶段切换

Step 4 判定当前阶段收尾后：更新 `status.md` 标记阶段完成
- 阶段2完成 → 进入 Step 6
- 阶段1完成 → 自动进入阶段2。**自动化模式例外但反向**: 若阶段1发现问题总数为 0，询问用户是否仍需进入阶段2（大概率无需），若用户不回应则自动结束。**交互模式例外**: 询问用户是否继续

### Step 6: 最终总结

此时加载 templates.md 的总结模板部分，生成 `final-summary.md`。如有遗留未修问题，追加"已知遗留问题"章节。

- **交互模式**: 在对话中为用户做优化总结
- **自动化模式（Git 仓库）**: 
  在对话中告知用户：**"优化分支 `codebase-optimizer/{日期}` 已推送至远端，共 N 个 commit，每个 commit 对应一轮优化。请创建 Pull Request 并交由人工 review 后合并。"**
- **自动化模式（非 Git 仓库）**: 在对话中做总结，提示备份文件在 `backups/` 目录中

## 风险操作定义（按操作类型而非严重度决定是否需要确认）

| 操作类型 | 需要确认 | 示例 |
|---------|---------|------|
| 文件删除 | ✅ 是 | 移除废弃文件 |
| 文件重命名 | ✅ 是 | 重构目录结构 |
| 接口签名变更 | ✅ 是 | 更改函数参数、重命名公开方法 |
| 注释补充 | ❌ 否 | 添加缺少的注释 |
| 代码格式化 | ❌ 否 | 修复缩进、空格 |
| 变量重命名（不改签名） | ❌ 否 | 局部变量改名 |

**交互/自动化模式对应的确认方式见"模式差异对照"表**。
